# 分域工作流 C：专业服务域（§14、§16、§19–§25）

> 本文件由 `dispatch.md` 按场景域拆分而来。主路由表见 `dispatch.md`，同域其他分支见 `dispatch-a-content.md`（内容创作域）、`dispatch-b-data.md`（数据票据域）。
> 全局约束：所有工作流强制遵循 `references/fact_discipline.md`；合同/招聘/绩效类产出必须由人终审，AI 只做起草与提示。

## §14 合同审查（采购 / 法务 / 财务视角）

适用：采购、法务、财务、业务人员审查各类合同（买卖/采购/服务/劳动/合作/知识产权/租赁等），识别风险点、缺失条款、版本差异。

**能力边界**：本 skill **不替代律师或专业法务**，审查结果仅为 AI 辅助参考。重大合同或复杂法律关系应交执业律师/企业法务最终复核。

**敏感字段（脱敏前置）**：审查产出含主体身份证号/统一社会信用代码时，按 `references/privacy_desensitization.md` **先询问**脱敏方式——内部使用可保留原文，对外分享再脱敏，不默认遮盖。

步骤：
1. 获取合同文本：用户直接粘贴、上传 Word/PDF/图片，或先经 §13 OCR 提取文字。
2. 判定合同类型：商事/服务/劳动/合作/知识产权/其他。
3. 按本文件内置工作流做三视角合同审查。
4. 内置审查维度（三视角）：
   - **通用结构**：主体信息、标的、金额、付款、交付、违约责任、争议解决、生效/终止。
   - **采购视角**：供应商资质与授权、交付/验收、质保、付款条件、违约罚则、保密与知识产权归属。
   - **法务视角**：合法性、权利义务对等、免责条款合理性、知识产权/保密/竞业、争议管辖/法律适用。
   - **财务视角**：价格与税率、付款节点、发票类型与时点、预算与成本归属、保证金/押金/预付款、退款与赔偿财务影响。
5. 输出：
   - 合同摘要（类型、主体、标的、金额、期限、关键义务）
   - 风险清单（位置 | 描述 | 高/中/低 | 建议修改）
   - 缺失条款提示与补充建议
   - 版本对比（若提供多版）：变更项、影响、需复核点
   - 总体风险评级 + 签署建议
   - **免责声明**：本结果由 AI 辅助生成，不构成正式法律意见。
6. 下游衔接：重大风险进周报/报告（周报模板见 assets/weekly-report-template.md），修改/跟进事项进入 §9 行动项追踪，常用合同条款沉淀进 §5 知识库。

**零依赖路径**：本场景无需外部 skill/连接器，直接粘贴合同文字/上传 Word/PDF 即可走内置三视角审查。

**常见异常处理**：
- 需要更专业的审查时，提示重大合同交执业律师/企业法务复核。
- 合同类型不明确 → 先问"这是买卖/服务/劳动/合作/知识产权/租赁中的哪类？"
- 用户要求正式法律意见 → 明确拒绝并建议"请咨询执业律师/企业法务，本结果仅为 AI 辅助参考"。
- 合同页数/条款过多 → 分段审查，先出总体摘要再逐条风险。

## §16 会议录音转文字（音频转写 → 纪要）

适用：用户上传会议录音（.mp3/.wav/.m4a）或任意音频，希望"先转成文字，再整理成纪要/行动项"。**本技能不自带 ASR（语音识别）引擎，只做调度与后续加工**，转写能力必须来自外部依赖。

**核心原则**：没有转写能力时，**宁可不干活，也要给出可落地的下一步**——绝不只回"我做不到"，也绝不伪造/猜测转写内容（违反事实纪律）。

**转写依赖四级阶梯（按最省事 → 最完整）**：
1. **腾讯会议 tmeet 连接器**（最省事，开会场景）：若用户用腾讯会议，引导去连接器页"信任"启用 `tmeet`；云录制自带转写，启用后直接拉取转写稿走 §1。
2. **宿主语音转文字能力**（长期自动化）：若宿主提供转写能力，优先调用它转写，再走 §1。
3. **本机 ASR 引擎（数据留本地）**：引导用户在本机部署 `faster-whisper`（详见 `assets/audio-asr-guide.md` 的实测安装/调用指引）；用户转写后把文字稿发回，走 §1。
4. **粘贴文字稿（零门槛）**：引导用户用任意现成工具先把音频转成文字，把文字稿发来，本技能直接走 §1 整理纪要。

**无依赖时的标准引导话术**（检测到音频但环境无任何转写能力时输出，模板见 `assets/audio-asr-guide.md`）：
> 检测到音频文件，但当前环境没有可用的转写能力（未启用腾讯会议、未安装语音转文字技能、本机也未配置 ASR）。你可以任选一种方式继续：
> ① 最省事：用任意工具转成文字稿发我，我直接整理纪要；
> ② 开会用腾讯会议 → 去连接器页信任「腾讯会议」即可自动转写；
> ③ 想长期自动化 → 接入宿主的语音转文字能力后告诉我；
> ④ 数据要留本地 → 本机自托管 faster-whisper（我可给安装指引）。
> 选哪个？或直接把转写好的文字粘贴给我也行。

步骤（环境具备转写依赖时）：
1. **转写**：经上述任一依赖把音频转为文字稿；尽量保留说话人分段（若引擎支持）。
2. **语种与格式**：中文音频默认简体输出；若引擎输出繁体（如部分 faster-whisper 默认），按用户习惯转为简体（通常转），可用 OpenCC `t2s` 处理。
3. **纪要整理**：把转写稿作为 §1 的输入，走"纪要/待办提取"工作流，产出结构化纪要 + 行动项。
4. **事实纪律**：转写稿属"待确认/推断"级来源，口语错误、同音字、口音导致的错字须在纪要中标注 `[转写待核对]`；关键数字、人名、条款须提示用户人工核对（见 `references/fact_discipline.md`）。
5. **下游衔接**：行动项 → §9；需生成周报/邮件 → §3；常用术语/与会人 → §5 知识库。

**零依赖路径**：本场景是唯一强依赖场景——音频→文字必须借助外部转写能力（tmeet / 宿主语音能力 / 本机 ASR）；但无依赖时，本技能仍给出 4 档可落地方案（粘贴文字稿 / 腾讯会议 tmeet / 宿主语音能力 / 本机 faster-whisper），不卡死、不伪造。

**常见异常处理**：
- 环境无任何转写能力 → 按 `assets/audio-asr-guide.md` 输出 4 档引导话术，让用户选一个执行。
- 转写稿是繁体 → 用 OpenCC `t2s` 转简体（需本机有 opencc-python-reimplemented）。
- 口语错误/同音字/口音 → 在纪要中标注 `[转写待核对]`，关键数字/人名提示人工核对。
- 音频质量差（远场/重叠/窄带） → 说明"当前音频质量会导致准确率下降，建议靠近麦克风录制或使用专业设备"。

## §19 翻译（文档 / 邮件 / 多语互译）

适用：用户需要把文字、文档片段、邮件、术语表在中英文或多语之间互译，或批量处理多语言内容。（现状：DeepL/Google Translate/Microsoft Translator 文件级保版已成熟，腾讯元宝/科大讯飞在中文场景表现突出），本技能**零依赖做文本/Markdown 互译**，文件级排版保留交给可选外部工具，不自建翻译引擎。

**能力边界**：本技能**不内置文件翻译引擎**，不直接调外部翻译 API（避免隐私外发）；只做文本/Markdown 级的语义翻译、术语强制、双语对照与"格式保留建议"。PDF/DOCX/PPTX 等需要保留原排版时，引导用户用 DeepL/腾讯元宝/讯飞等文件级翻译工具（可选增强）。

步骤：
1. **定参数**：确认源语言（可自动识别）、目标语言、领域/术语表（如有）、是否要双语对照。
2. **翻译**：保留原文结构（标题/列表/段落/表格），不臆造；术语表强制映射到指定译法。
3. **质量标注**：专有名词（公司名/人名/产品名）保留原文或标注"【译名待核对】"；低资源语言/谚语/文化梗标注"【意译，需母语复核】"。
4. **格式保留建议**：若输入是 PDF/DOCX 等，提示"纯文本翻译会丢失排版，建议用 DeepL/元宝/讯飞做文件级保版"。
5. **下游衔接**：翻译后文档可经 §2 总结、§5 知识库沉淀、§3 转邮件。

**零依赖路径**：本场景无需外部 skill/连接器，直接粘贴文字/Markdown/术语表即可完成互译。

**常见异常处理**：
- 输入是 PDF/DOCX 要保版 → 说明纯文本会丢排版，引导用 DeepL/元宝/讯飞文件级翻译（可选）；或先 OCR/提取文字再翻。
- 专有名词被误译 → 提供术语表让用户补充，强制重新映射。
- 法律/医疗/合同翻译 → 明确提示"AI 翻译不替代专业认证译员，关键条款需人工/专业复核"。
- 低资源语言质量差 → 标注"【该语种质量有限，建议人工复核】"，不掩盖。

## §20 招聘 HR（JD 起草 / 简历初筛 / 面试提纲）

适用：HR、招聘负责人、业务面试官、创业者，需要起草岗位 JD、批量初筛简历、准备面试问题、撰写拒信或 offer。（现状：General/GenAI/Agentic 三层；"AI prepares, humans decide" 合规铁律；EEOC 偏差审计、EU AI Act 候选人知情权）。

**能力边界**：本技能**不替代最终录用决策、不自动拒绝任何候选人**；只做"生成与辅助排序"，人做终审。不直连 ATS，不做合规偏差审计（但会提示合规要点）。

步骤：
1. **JD 起草**：输出角色摘要、影响力导向的职责（5-7 条）、硬性要求 vs 加分项、薪资范围（建议透明）、福利、申请方式；**强制去性别词、去不必要门槛**（如"10 年经验做 5 年技术"）。
2. **简历初筛打分卡**：上传岗位要求 + 简历（文字/PDF/Word，批量可 CSV）；按"匹配度(1-10) + 优势 + 顾虑 + 建议动作(推进/hold/过) + 针对性面试题"逐人评估；**不惩罚职业空窗、非传统路径**。
3. **面试提纲**：按岗位生成 STAR 行为题 + 情景题 + 技术题 + 文化题，每项附评分卡（优秀/合格/待改进标准）与追问。
4. **沟通草稿**：拒信（善意、具体、留门）、offer（兴奋、清晰、下一步）。
5. **合规提示**：附"AI 仅辅助、最终决策在人；注意 EEOC/EU AI Act 合规，需人工偏差复核，绝不自动拒人"。
6. **下游衔接**：候选人信息进 §5 知识库；面试待办进 §9 行动项；JD 可经 §3 转邮件。

**零依赖路径**：本场景无需外部 skill/连接器，直接粘贴岗位要求+简历即可做 JD/打分卡/提纲；简历为图片/扫描件时可选经 §13 OCR 解析。

**常见异常处理**：
- 用户要求"自动拒人/自动发 offer" → 明确拒绝："本技能不自动拒人、不自动发 offer，最终决策与发送由你确认。"
- 简历是图片/扫描 PDF → 先经 §13 OCR 或提示上传文字版。
- 偏见风险（如只筛名校） → 主动提示"建议按能力优先（skills-first）评估，避免历史偏见放大"，并标注需人工偏差复核。
- 没给薪资范围 → JD 中标注"【薪资待补充】"，并建议透明薪资以提升响应率。

## §21 日程 / 会议排期

适用：用户需要约会议、找多方空闲时间、协调会议室、检查时间冲突、生成会议邀请。（现状：飞书日历AI/钉钉按组织架构一键发起+匹配空闲、Calendly/Reclaim.ai 自动排期、飞书智能会务查忙闲→建日程→加参与者/会议室→订阅回复动态调整）。

**能力边界**：本技能**未授权时不读取用户日历隐私**；**不自动发送会议邀请、不修改他人日程**（与全局安全边界一致）。授权连接器后只读忙闲以给出建议。

步骤：
1. **收需求**：参会人、时长、偏好时段（上午/下午）、时区、是否需要会议室。
2. **冲突检查**：若用户提供多方已有日程，检查重叠，标注 🚨"时间冲突"并给替代时段。
3. **排期建议**：给出 2-3 个候选时段（含理由，如"全员空闲且避开核心专注块"）；跨时区时给出各地对应时间。
4. **会议邀请草稿**：生成可复制的邀请文案（主题/时间/参会人/议程/会议室）。
5. **授权后读忙闲**：若用户已授权 feishu/dingtalk/wecom 日历连接器，调用其读忙闲以给出精准空闲时段；否则基于用户提供文字生成建议。
6. **下游衔接**：确认的日程可进 §4 晨间简报；会议待办进 §9 行动项。

**零依赖路径**：本场景无需外部 skill/连接器，直接说明参会人/时间窗/会议室需求即可生成排期建议与会议邀请草稿。

**常见异常处理**：
- 未授权日历连接器 → 明确告知"当前未读你的日历，基于你提供的时间窗给建议"；若想自动读忙闲，去连接器页信任 feishu/dingtalk/wecom。
- 多方时间冲突 → 标注 🚨 冲突，给 2-3 个替代时段，不擅自改任何人日程。
- 用户要求"直接发邀请/改他人日历" → 明确拒绝："本技能不自动发邀请、不改他人日程，请在对应 App 确认发送。"
- 跨时区算错 → 明确列出各地对应时间并标注"时区以你确认为准"。

## §22 合同起草（按要素生成初稿，与 §14 审查互补）

适用：用户要"起草/拟一份合同"而非"审查现有合同"——提供合同类型与关键要素，AI 生成可用初稿。（现状：起草与审查已分化为不同技能；起草"基本解决"，AI 快速生成可用初稿，-80% 耗时；Spellbook/Iro/Juro/DraftWise 等工具成熟；GenieAI 等面向非律师的预批准模板兴起）。本技能**零依赖生成文本初稿**，不自建合同引擎。

**能力边界**：本 skill 不替代执业律师/法务终审，不做正式法律意见；生成的是"可用的谈判起点"，格式条款、责任限制、管辖条款等高风险条款须人工复核。

**敏感字段（脱敏前置）**：合同含主体身份证号/统一社会信用代码/银行账号时，按 `references/privacy_desensitization.md` **先询问**脱敏方式——内部使用可保留原文，对外分享再脱敏，不默认遮盖。

步骤：
1. **收要素**：合同类型（买卖/服务/采购/合作/劳动/租赁/知识产权等）、双方主体（名称/信用代码/地址/联系人）、标的或服务内容、金额与付款节奏、期限、交付/验收标准、违约责任偏好、管辖与争议解决偏好。
2. **起草**：生成结构化初稿——标题 + 合同编号占位 + 双方信息 + 鉴于条款 + 正文条款（定义/标的/价格与付款/交付验收/权利义务/违约责任/保密/知识产权/不可抗力/争议解决/生效终止）+ 签署页。
3. **条款可选配置**：付款节奏（预付/里程碑/月结）、违约金比例、保密期限、知识产权归属、管辖地——向用户列出选项，不擅自定义。
4. **风险自查（内嵌 §14 视角）**：对生成初稿自查通用结构完整性（主体/标的/金额/期限/违约/争议六要素是否齐备），标注"【建议律师复核】"的高风险条款（格式条款、责任限制、管辖、违约金过高）。
5. **待确认项清单**：金额/日期/比例等需要用户填实的字段，逐一列出【待填】。
6. **下游衔接**：初稿 → §14 合同审查自审 → §3 转邮件发给对方 → §9 行动项跟进签署 → 常用条款沉淀 §5 知识库。

**零依赖路径**：本场景无需外部 skill/连接器，直接说明合同类型与要素即可生成文本初稿（Markdown）；需要正式 Word 版时由宿主的文档处理能力排版。

**常见异常处理**：
- 用户只说"起草个合同"没说类型 → 先问"这是买卖/服务/采购/合作/劳动/租赁中的哪类？双方是谁？标的/金额大概多少？"
- 要素严重不足（没金额没期限） → 生成框架初稿 + 逐项列出【待填】，不臆造金额日期。
- 用户要求正式法律意见/保证合同无懈可击 → 明确告知"初稿需律师/法务复核后签署，本结果仅为 AI 辅助生成"。
- 复杂交易（并购/股权/涉外） → 主动提示"建议交执业律师处理，本技能只适合常规商务合同"。
- 含敏感字段 → 按 `references/privacy_desensitization.md` 先问脱敏方式。

## §23 新媒体文案 / 社交内容（多平台）

适用：用户要写公众号、小红书、抖音/视频号脚本、朋友圈、微博、标题、slogan、活动宣传、种草文案。（现状：AI 辅助内容产出提升约 3 倍；平台算法偏好真实、有互动、非 AI 味的内容；广告法合规是红线）。本技能**零依赖生成文本**，不做平台发布。

**能力边界**：不保证爆款（受平台算法与热点影响）；不替代专业投放策略；不做平台发布操作；AI 标识只做提示与话术，**最终是否标注由发布者（用户）完成**。

步骤：
1. **定平台与调性**：平台（公众号/小红书/抖音/视频号/朋友圈/微博）、目标受众、调性（专业/种草/幽默/温暖/权威）、字数或时长限制。
2. **定内容**：主题、核心卖点/信息（最多 3 个）、行动召唤 CTA（关注/评论/购买/报名）、是否要标题备选。
3. **生成**：按平台格式输出——
   - 公众号：标题 3 个备选 + 导语 + 小标题结构 + 正文 + 结尾 CTA + 摘要建议。
   - 小红书：标题 + 正文（emoji 适度、分段、带话题标签 #）+ 首图文字建议。
   - 抖音/视频号：前 3 秒钩子 + 分镜脚本（画面/口播/字幕）+ 结尾 CTA + 文案 30 字内。
   - 朋友圈：≤ 200 字 + 配图建议 + 互动钩子。
   - 通用：slogan 3-5 个备选（简短、可注册性提示）。
4. **合规自查（强制，两项硬要求）**：
   - **广告法红线**：不夸大（"最""第一"等极限词提示风险）、不虚假宣传、数据引用标注来源、医疗/金融等特殊行业提示资质要求。
   - **AI 生成合成内容标识**（2026-09-01 强制性国标）：交付时**主动提示用户加显式标识**——文案在文首或文末显著位置标注"AI 辅助创作"；配图/封面加显著角标；视频脚本在画面或语音中提示；同时建议写入文件元数据的隐式标识。**仅用 `#AI#` 话题标签不算合规**（2026-05 已有因此被处罚的案例）。对内使用不强制，对外发布必须有。涉及数字人/换脸换声时额外提示肖像权与授权风险。
   自查结果以清单形式附在文案末尾，格式：`[PASS] 无极限词` / `[WARN] "最"字需替换` / `[必须] 对外发布请加 AI 标识`。
5. **去 AI 味**：删除"首先/其次/总而言之"式模板腔、过度排比；口语化改写；长句拆短句；避免千篇一律的开头。
6. **下游衔接**：文案可转 §3 邮件/消息；爆款素材沉淀 §5 知识库；发布后数据可进 §12 数据分析。

**零依赖路径**：本场景无需外部 skill/连接器，直接说明平台+主题+调性即可生成多版文案。

**常见异常处理**：
- 没说平台/调性 → 先问"发哪个平台？给谁看？什么风格？"；不明确时默认公众号专业风并给 2 个备选风格。
- 要求"保证爆款" → 说明"爆款受算法与热点影响，我能按平台规律优化结构，但不承诺效果"。
- 涉及医疗/金融/教育等敏感行业 → 主动提示"需核实资质与广告法限制，建议合规审核后发布"。
- 文案被平台判营销号/AI 味 → 提供去 AI 味重写版，口语化、加真实细节。
- 用户不愿加 AI 标识 → 明确告知这是《标识办法》与强制性国标的法定义务，对外发布不标注存在被平台处置与行政处罚的风险；若内容为纯人工改写且 AI 仅做润色，可据实说明并让用户自行判断，但**不得建议规避标识**。

## §24 流程图 / 思维导图 / 架构图（diagram-as-code）

适用：用户要画流程图、时序图、思维导图、架构图、ER 图、UML 类图、甘特图。（现状：Mermaid/PlantUML/D2 为最稳定方案，Mermaid 是最安全默认；AI 生成 diagram 代码已成为非工程师也能用的成熟能力）。本技能**零依赖输出代码文本**，不自建绘图引擎。

**能力边界**：本 skill 不自动渲染图片；输出 Mermaid/PlantUML 代码 + 渲染指引（mermaid-cli / mermaid.live / Typora / Obsidian 等）。复杂图（大架构、多节点）需人工调整布局。

步骤：
1. **定图类型**：流程图（flowchart）/ 时序图（sequenceDiagram）/ 思维导图（mindmap）/ 架构图（flowchart/graph）/ ER 图（erDiagram）/ 类图（classDiagram）/ 甘特图（gantt）。
2. **收集要素**：流程类——起点/步骤/分支/结束、判断条件；时序类——参与者/消息顺序；架构类——分层/组件/依赖关系；思维导图——中心主题/一级分支/叶子。
3. **生成代码**：默认用 **Mermaid**（最安全默认），复杂对象模型可转 PlantUML；输出代码块 + 注释说明 + 渲染指引。
4. **迭代**：用户反馈后修改节点命名、分支条件、方向（TB/LR）、样式（classDef 主题色）。
5. **渲染指引**：给出 1-2 种渲染方式（mermaid.live 在线 / 本地 mermaid-cli `mmdc -i input.mmd -o out.png` / 笔记软件内嵌），不假设用户装了任何工具。
6. **下游衔接**：图可嵌入 §2 文档总结、§17 周报、§6 PPT 大纲；流程说明沉淀 §5 知识库（SOP）。

**零依赖路径**：本场景无需外部 skill/连接器，直接描述流程/结构即可生成 Mermaid/PlantUML 代码文本。

**常见异常处理**：
- 用户只说"画个图"没说类型 → 先问"是流程图/时序图/思维导图/架构图中的哪种？大概描述一下内容"。
- 用户要 PNG/SVG 图片 → 给渲染指引（mermaid.live 导出 / mermaid-cli 命令），不假装已渲染。
- 节点太多一图塞不下 → 建议拆分多图（主流程 + 子流程），或改用分层架构图。
- 语法报错渲染失败 → 自查并修复 Mermaid 语法（节点 id 冲突、引号转义），重试 ≤3 次后给简化版。
- 中文渲染乱码 → 说明"Mermaid 中文需选支持 CJK 的渲染器（如 mermaid-cli + 中文字体），在线工具一般正常"。

## §25 OKR / 绩效自评 / 年度复盘

适用：季度 OKR 制定、绩效自评、上级评审草稿、360 反馈汇总、年度复盘、述职材料。（现状：已演进为连续绩效管理，AI 起草评审评论可省约 60% 管理者写作时间；Lattice/15Five/Culture Amp 等工具成熟；AI 辅助开放文本反馈分析）。本技能**零依赖起草文本**，评分/等级/晋升由人定。

**能力边界**：本 skill 不虚报数据、不做绩效等级判定、不替代绩效系统；只做起草与整理，最终评分由主管/HR/评审委员会决定。

步骤：
1. **定类型**：OKR 制定 / 绩效自评 / 上级评审草稿 / 360 反馈汇总 / 年度复盘 / 述职报告。
2. **收集素材**：上期目标与结果、本期工作成果（数据/项目/里程碑）、用户或同事反馈、公司目标（用于对齐）。
3. **OKR 制定**：
   - O（目标）：有方向感、鼓舞人心、不超过 3 条。
   - KR（关键结果）：可量化（数值/百分比/里程碑）、有挑战但可达、可验证；每条 KR 附数据来源或测量方式。
   - 对齐：注明与公司/部门目标的关联。
4. **绩效自评 / 上级评审**：成果（用事实与数据，不用"努力""加班"等无效描述）+ 亮点 + 不足（诚实、不自我贬低）+ 改进计划 + 对下期目标的建议。上级评审视角补充：与目标完成度、团队影响、成长性。
5. **年度复盘**：年度关键成果时间线 + 数据亮点 + 3 条经验沉淀 + 3 条下年改进 + 资源/支持需求。
6. **事实纪律**：所有数据标注来源；未确认成果标 `[待确认]`；不编造业绩、不虚报数字。
7. **下游衔接**：绩效材料可进 §17 周报/述职、§2 总结；改进计划进 §9 行动项；常用表达沉淀 §5 知识库。

**零依赖路径**：本场景无需外部 skill/连接器，直接提供目标/成果/数据即可起草 OKR、自评、复盘、述职材料。

**常见异常处理**：
- 用户没给任何素材 → 给空白模板 + 引导问题（"上季度 3 个最重要的成果是什么？"），或基于已知会话内容生成并标注假设。
- 目标写得太虚（"提升用户体验"） → SMART 化：加时间、量化标准、负责人、衡量方式。
- 用户要求"帮我打绩效等级" → 明确拒绝："最终评分由主管/HR 决定，我只帮你起草材料和汇总事实。"
- 含敏感绩效信息 → 按 `references/privacy_desensitization.md` 先问脱敏方式。
- 数据前后矛盾 → 列出差异并让用户确认，不擅自取一个。
