# 需求满足度评估规范

条件触发阶段（**阶段 R**）使用。对应验收标准「能不能做、改哪里、多久、缺什么，一眼看清」。

## 触发条件

用户在**任何阶段**（最常见是阶段0 说完项目名之后）抛出这类意图，立即进入阶段 R：

- 「我要用 XX 做 YY 功能，能不能支持？」
- 「这个需求要改哪些地方？大概多久？」
- 「帮我评估一下这个项目能不能满足我们的需求」
- 「对比一下这几个功能点哪些要自己开发」

**没提需求 → 不走阶段 R**，按原七阶段产出上手报告即可。

---

## R1 · 需求解析与澄清（多轮确认）

### 为什么这里允许多轮追问

阶段0 的原则是「假设先行、表是告知不是卡流程」——那条规则**只约束目标/深度/形态这类偏好维度**，
即"不要为了这些偏好去连环追问用户"。

需求本身则不同：**需求理解错了，后面所有代码审查和工时估算全废**。所以这里反过来——
**有歧义必须问清，问不清不许进入 R2。** 这是本技能唯一允许多轮追问的环节。

但追问必须**批处理**，不是连环单问：

| 约束 | 规则 |
|------|------|
| 每轮问题数 | **≤ 5 个**，一次把所有歧义摊开 |
| 每个问题 | 必须给 A/B/C 选项 + **默认值**（不回复就按默认走） |
| 最多轮次 | **3 轮**。第 3 轮仍有歧义 → 冻结为「假设值」，写进风险清单，**不再追问** |
| 中断策略 | 用户说「你看着办 / 都行 / 确认」→ 立即冻结，全部按默认值走 |

### 第一步：需求拆解成原子功能项

把用户的一段话拆成**可独立判定的功能项** `FR-01 … FR-NN`。拆分标准：

- 一项 = 一个可验证的行为（"导出 Excel" 是一项，"系统好用" 不是一项）
- 一项只包含**一个**判定结论；若内含"且/或者"，继续拆
- 非功能诉求（性能、并发量、部署方式、界面语言）单独编号，标注 `[NFR]`

拆完先做**清晰度标记**：

| 标记 | 含义 | 处置 |
|------|------|------|
| 清晰 | 无二义，可直接进 R2 检索 | 直接判定 |
| 歧义 | 有多种合理解读，结论会不同 | 列入澄清表 |
| 缺口 | 缺关键信息（量级/边界/现有环境） | 列入澄清表 |

### 第二步：输出《需求澄清确认表》

```markdown
## 需求澄清确认表（第 1 轮 / 最多 3 轮）

已明确的功能项（不再问）：FR-01 登录鉴权、FR-03 列表分页

| # | 关联项 | 我的理解 | 歧义点 | 请选一个（不回复我按【默认】走） | 默认 |
|---|--------|---------|--------|--------------------------------|------|
| Q1 | FR-02 | 你要的"多租户"指数据隔离 | 隔离粒度没说 | A 独立库 / B 共享库+tenant_id / C 独立 schema | B |
| Q2 | FR-05 | "审批流"要能配置 | 是否要可视化流程设计器 | A 需要拖拽设计器 / B 代码里配流程即可 | B |
| Q3 | FR-07 | 导出要 Excel | 量级与方式 | A 万级同步导出 / B 十万级异步+下载中心 | A |

**回复方式**：直接写「Q1=B, Q2=B, Q3=A」，或只改有意见的行。
**全部按默认走请回复「确认」。**
```

要点：

- **「我的理解」列必须写** —— 让用户先看到你理解成什么，比直接问"你什么意思"高效十倍
- **默认项要选最保守/最常见的那个**，并说明理由一句
- 不要问能通过读代码/文档自己查到的事实（那属于 R2）

### 第三步：冻结需求基线

```markdown
## 需求基线 v1（冻结）

| 项 | 需求描述（澄清后） | 来源 | 状态 |
|----|-------------------|------|------|
| FR-01 | 账号密码登录 + JWT，有效期 8h | 用户原话 | 已确认 |
| FR-02 | 共享库 + tenant_id 行级隔离 | Q1=B | 已确认 |
| FR-05 | 流程在代码/配置中定义，无需设计器 | Q2=默认 | 假设值 |

本基线基于 1 轮澄清冻结；标注「假设值」的项若后续证伪，需重跑 R3 判定。
```

**基线不冻结 → 不许进 R2。**

## R2 · 需求驱动的代码审查

不是全量代码 review（那不是本技能职责），而是**每个 FR 定向找证据**：

1. **关键词检索**：从 FR 提炼 3-5 个中英文关键词（含同义词、常见缩写），Grep 全库
2. **定位落点**：命中 → 记 `路径:行号`；未命中 → **记录检索了哪些关键词、在哪些目录搜的**
3. **找扩展点**：查 SPI / 插件机制 / 抽象类 / 配置项 / 事件钩子（阶段2 的 2.4 已产出，直接复用）
4. **判影响面**：改动会牵动哪些模块（对照阶段2 的模块依赖表）

**"不支持"是最难下的结论**——必须能说出"我搜了 X、Y、Z 三个关键词，在 src/ 全量未命中"，
不能凭"我记得它没这功能"下判断。

## R3 · 满足度判定（四分类）

| 结论 | 判定标准 | 典型动作 |
|------|----------|----------|
| ✅ **原生支持** | 已实现，配置或调用即可 | 写配置项/调用方式，0 开发量 |
| 🔧 **改造支持** | 有相近能力但不满足，需改已有代码 | 列出改动点，动核心代码 |
| 🧩 **扩展支持** | 有扩展机制，新增实现即可，不动核心 | 实现接口/插件，风险最低 |
| ❌ **不涵盖** | 项目定位上就没有，无相近能力 | 需自建/外挂/换方案 |

**「能否实现」三档**：能 / 部分能 / 不能 —— 必须与四分类对应，不许出现「🔧 改造支持 + 不能实现」。

### 每条 FR 的九个字段（缺一不可）

```markdown
### FR-05 审批流程可配置 🔧 改造支持

- **用户原话**：「审批流程要能自己配，不能写死在代码里」
- **能否实现**：部分能（流程可配置，但无可视化设计器）
- **判定依据**：`workflow/engine/FlowEngine.java:112` 已有多节点流转；
  `workflow/parser/` 目录不存在，全库检索 "designer/drag/可视化" 未命中
- **实现方式**：新增 YAML 流程定义 + 解析器，接入现有 FlowEngine
- **修改位置**：
  | 文件:行号 | 改什么 | 类型 |
  |-----------|--------|------|
  | `workflow/engine/FlowEngine.java:112` | 流程启动改为从定义加载 | 改 |
  | `workflow/model/FlowNode.java:0` | 新增节点/网关模型 | 新增 |
  | `resources/application.yml:38` | 增加流程定义路径配置 | 改 |
- **工作量**：M · 3-5 人日（依据：新增 1 个模块 ~800 行 + 改 1 处核心链路 + 配套单测）
- **风险与波及面**：FlowEngine 是下单、退款两条链路共用，改动需回归两条链路；
  原硬编码流程需保留兼容开关
- **验证方式**：用 YAML 定义一条 3 节点流程，走完下单审批，观察 `flow_instance` 表状态流转
```

「修改位置」必须精确到**文件:行号**，新增文件写 `:0` 并标注 `新增`。
「工作量」必须给**估算依据**，只写"3 人天"视为不合格。

### 工作量刻度表

| 档 | 人日 | 典型特征 |
|----|------|----------|
| **XS** | 0.5 | 改配置/改 1 个文件 ≤50 行，有现成文档 |
| **S** | 1-2 | 单模块内改动，有现成扩展点，无需动核心链路 |
| **M** | 3-5 | 跨模块，需新增类 + 改已有逻辑 + 单测 |
| **L** | 1-2 人周 | 核心链路改造，或新增一个子系统 |
| **XL** | > 2 人周 | 项目架构上根本不支持，接近重写 → **优先建议换方案** |

**估算前提必须写明**（否则数字无意义）：

```markdown
> 估算前提：1 名熟悉本项目的后端；含自测与单测；不含联调、压测、UI 走查；
> 未计入 fork 后与上游版本同步的长期成本。
```

## R4 · 不涵盖功能的补充方案

每个 ❌（以及"部分能"中缺失的那部分）必须给补充方案。**只写"不支持"视为不合格。**

```markdown
### 缺口 G-01：可视化流程设计器（FR-05 的一部分）

- **为什么没有**：项目定位是「嵌入式流程引擎」，官方明确不提供 UI（README:45 "headless by design"）
- **补齐路径对比**：
  | 路径 | 做法 | 工作量 | 升级影响 | 评价 |
  |------|------|--------|----------|------|
  | A 自建 | 前端 React + 后端定义存储 | L 1-2 人周 | 无（独立模块） | 可控但慢 |
  | B 接第三方 | 集成 bpmn-js + 转换层 | M 3-5 人日 | 低（依赖 1 个 npm 包） | **推荐** |
  | C 改需求 | 接受 YAML 配置流程 | 0 | 无 | 最快，牺牲易用性 |
- **推荐**：B（理由：bpmn-js 是 BPMN 标准实现，转换层约 300 行，且与核心解耦）
- **若不补的影响**：运营无法自助改流程，每次调整需发版
```

**升级影响**这一列不能省 —— 开源项目改造最贵的成本是 fork 之后再也无法跟上上游，
必须显式评估「改在核心里」还是「挂在外面」。

## R5 · 汇总与结论

```markdown
## 汇总

| 结论 | 项数 | 人日小计 |
|------|------|----------|
| ✅ 原生支持 | 4 | 0.5（配置） |
| 🧩 扩展支持 | 3 | 4 |
| 🔧 改造支持 | 2 | 7 |
| ❌ 不涵盖 | 1 | 5（外挂补齐） |

- **基准工作量**：16.5 人日（区间 13-21）
- **关键路径**：FR-05 流程引擎改造 → FR-08 权限模型改造（后者依赖前者的节点模型）
- **风险 Top3**：
  1. FlowEngine 改动覆盖下单/退款两条链路，回归面大
  2. 行级隔离需改所有查询，遗漏即越权（FR-02）
  3. fork 后与上游同步成本未计入
- **结论建议**：**改造后用** —— 控制在 16 人日内可满足 10/10 项需求；
  若可接受 YAML 配流程（方案 C），可压到 9 人日
```

结论建议三种：**直接用** / **改造后用（控制在 X 人日内）** / **不建议用（说明换什么）**。

## 优质判据

- [ ] 需求是否拆成了原子功能项并编号？
- [ ] 歧义项是否走了澄清表（批处理 ≤5 问/轮、给默认、≤3 轮）？
- [ ] 需求基线是否冻结后才开始 R2？
- [ ] 每条 FR 是否四分类 + 「能否实现」三档，二者一致？
- [ ] 「判定依据」是否有 `路径:行号`，或未命中时写明了检索关键词与范围？
- [ ] 「修改位置」是否精确到行号、标注改/新增？
- [ ] 「工作量」是否给了档位 + 人日 + 估算依据 + 估算前提？
- [ ] ❌ 项是否都给了 ≥2 条补齐路径 + 推荐 + 升级影响？
- [ ] 汇总表是否有总人日、关键路径、风险 Top3、明确建议？

## 常见错误

- ❌ 需求没澄清就开评（理解错 → 全盘返工）
- ❌ 连环单问（问一个等一个，把用户耗死）→ 应批处理
- ❌ 澄清问题不带默认选项（用户不回就卡住）
- ❌ 无限追问超过 3 轮（应冻结为假设值并标风险）
- ❌ 判定写「不支持」但没写检索了什么（无法复核）
- ❌ 修改位置只写目录不写行号（等于没定位）
- ❌ 工作量只写数字不给依据（无法评审）
- ❌ ❌ 类需求只说"要自己开发"（没给路径和成本 = 没评估）
- ❌ 把"配置一下就能用"也算成人日（虚报工时）
