# 需求满足度评估报告模板

阶段 R 产出。可独立成篇，也可作为 `onboarding-report.md` 的章节 R 嵌入。
需求项 ≤3 条时可压缩为「总览表 + 缺口方案 + 结论」三段；>3 条时按完整结构输出。

```markdown
# <项目名> 需求满足度评估报告

> 评估对象：<项目名 + 版本> ｜ 需求基线：v<N>（<日期> 冻结）
> 估算前提：1 名熟悉本项目的后端；含自测与单测；不含联调、压测、UI 走查；
> 未计入 fork 后与上游同步的长期成本。

## R0. 一句话结论

<能不能用、要投多少人日、最大风险是什么。三句话内。>
**建议**：直接用 / 改造后用（控制在 X 人日内）/ 不建议用（换 <方案>）

## R3. 逐项评估

### FR-01 账号密码登录 + JWT ✅ 原生支持

- **用户原话**：「先用账号密码登录就行」
- **能否实现**：能
- **判定依据**：`config/SecurityConfig.java:44` 已装配 `JwtAuthenticationFilter`；`application.yml:22` 有 `jwt.expire`
- **实现方式**：改配置项，无需改代码
- **修改位置**：
  | 文件:行号 | 改什么 | 类型 |
  |-----------|--------|------|
  | `resources/application.yml:22` | `jwt.expire: 28800`（8h） | 改 |
- **工作量**：XS · 0.5 人日（依据：仅配置调整 + 登录/登出/过期三类冒烟验证）
- **风险与波及面**：无代码改动，无波及
- **验证方式**：登录后取 token，8 小时后请求应返回 401

<其余 FR 按同样九个字段展开。「改造支持」与「不涵盖」项必须展开；「原生支持」项可只留总览表一行。>
```

# 交付自检清单

交付前逐条打勾，**任一为否则不能交付**：

- [ ] 需求是否拆成原子项并编号（FR-01…）？
- [ ] 歧义项是否走了澄清表（每轮 ≤5 问、带默认选项、≤3 轮）？
- [ ] 需求基线是否已冻结？假设值是否单独标注？
- [ ] 每个 FR 的四分类与「能否实现」三档是否一致（无自相矛盾）？
- [ ] 每条判定依据是否有 `路径:行号`，或未命中时写明检索关键词与范围？
- [ ] 「修改位置」是否精确到行号、标注改/新增？
- [ ] 每条工作量是否有档位 + 人日 + **估算依据**？
- [ ] 报告头部是否写明**估算前提**（含什么/不含什么）？
- [ ] 每个 ❌ 项是否有 ≥2 条补齐路径 + 推荐 + **升级影响**？
- [ ] 汇总是否有总人日、区间、关键路径、风险 Top3、明确建议？
- [ ] **`check_fit_report.py` 是否跑过且无 ERROR？**
