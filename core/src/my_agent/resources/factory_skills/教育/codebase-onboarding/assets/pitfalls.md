# 踩坑点规范

阶段5 使用。对应验收标准「踩坑点提醒有意义，可以避免后续问题」。

## 四段式（缺一不可）

```markdown
### 坑 3：构造器循环依赖导致启动失败

- **现象**：启动报 `BeanCurrentlyInCreationException: Error creating bean with name
  'a': Requested bean is currently in creation: Is there an unresolvable circular reference?`
- **原因**：A 的构造器要 B，B 的构造器要 A。构造阶段双方都没实例化完，
  三级缓存无法提前暴露引用（字段注入可以，因为它先 new 出对象再填属性）。
- **解决**：
  1. 推荐：重构——把双方共同依赖抽成第三个类 C，A、B 都依赖 C
  2. 应急：一方改用 setter/字段注入（只是掩盖，不推荐）
  3. 兜底：`@Lazy` 延迟其中一方初始化
- **如何避免**：团队统一约定**只用构造器注入**，让循环依赖在启动期就暴露；
  CI 加一条检查：禁止字段上出现 `@Autowired`（ArchUnit 可实现）。
```

四段职责：
- **现象**：用户会看到的**确切**报错文本或行为（能搜到的那种）
- **原因**：底层机理，不是"因为配置错了"
- **解决**：可复制的命令/代码，多个方案要给优先级
- **如何避免**：编码习惯、配置约定、CI 检查项

**缺「如何避免」视为不合格**——只解决不复发的坑会反复踩。

## 优先级排序

| 优先级 | 类别 | 为什么排前面 |
|--------|------|--------------|
| P0 | 环境依赖（JDK/Node/Python 版本、系统库） | 装不上就什么都做不了 |
| P0 | 版本兼容（大版本行为变更） | 影响面最大 |
| P1 | 配置错误（默认值的坑） | 高频 |
| P1 | API 误用（看着能跑实际有隐患） | 静默出错最难查 |
| P2 | 性能陷阱（连接池、N+1、大对象） | 上线后才暴露 |
| P2 | 升级迁移 | 有明确触发条件 |

## 可预防性判定

写入前问自己：**这条能不能让人提前做一件事来避免？**

| 能做 | 不能做 |
|------|--------|
| "用构造器注入，循环依赖启动即暴露" | "注意循环依赖问题" |
| "JDK 17+，因为 Spring Boot 3.x 基线是 17" | "版本要匹配" |
| "配置项默认是 false，生产需要显式开启" | "配置要注意" |

后者一律不写。

## 获取踩坑点的渠道

按可信度排序：

1. **项目自身的 ISSUE / FAQ / troubleshooting 文档**（最可信，标注 URL）
2. **扫描发现的模式**（如全字段注入 → 循环依赖风险；无连接池配置 → 连接耗尽）
3. **版本差异**（构建文件里的版本 + 官方迁移指南）
4. **社区讨论**（Stack Overflow、掘金、知乎，标注来源与时间）

**禁止凭记忆编造报错文本。** 报错信息要来自上述渠道之一，或标注"常见报错（未在本项目验证）"。

## Spring DI 高频踩坑（可作内置检查表）

| 坑 | 现象关键词 | 预防 |
|----|-----------|------|
| 构造器循环依赖 | `BeanCurrentlyInCreationException` | 统一构造器注入 |
| 字段注入导致单测必须启动容器 | 测试慢、难以 mock | 构造器注入 |
| 同接口多实现未指定 | `NoUniqueBeanDefinitionException` | `@Qualifier` 或 `@Primary` |
| Bean 未扫描到 | `NoSuchBeanDefinitionException` | 启动类包路径覆盖被扫描包 |
| prototype 不调用销毁回调 | 资源泄漏 | 手动释放或用 `@PreDestroy` 配合 singleton |
| `@Transactional` 同类内部调用失效 | 事务没生效 | 走代理对象调用或抽出独立类 |
| `@Value` 取不到配置 | 值为 null 或占位符原样输出 | 检查配置文件是否被加载 |

## 优质判据

- [ ] 每条四段齐全
- [ ] 现象是可搜索的确切报错/行为
- [ ] 「如何避免」给出可执行的动作（不是"注意"）
- [ ] 按 P0/P1/P2 排过序
- [ ] 报错文本有出处（项目文档/issue/扫描发现），不是编的
- [ ] 数量适中：核心能力 3-8 条，不凑数

## 常见错误

- ❌ 写"注意版本兼容性"就完事（等于没写）
- ❌ 只有现象和解决，没有原因（下次换个形式又不认识了）
- ❌ 编造报错文本（用户搜不到，失去信任）
- ❌ 罗列 20 条浅坑（不如 5 条深坑）
