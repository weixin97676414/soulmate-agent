# 能力清单规范

阶段3 使用。对应验收标准「核心能力展示清晰」。

## 三级分层

| 层级 | 判定标准 | 建议数量 |
|------|----------|----------|
| **核心能力** | 去掉它这个项目就不成立；README 首屏强调；架构上处于中枢 | 3-8 条 |
| **常用能力** | 日常使用高频，文档/示例覆盖多 | 8-20 条 |
| **进阶能力** | 需要理解内部机制才能用好；误用有风险 | 按需，≤10 条 |

**宁可少而准，不要多而全。** 列 40 条等于没列。

## 每条能力的字段

```markdown
### C-03 依赖注入与 Bean 管理 ★★★

- **一句话**：容器负责创建对象并把它需要的东西送进来，业务代码不 new 依赖
- **适用场景**：任何需要解耦组件、需要单测、需要按环境切换实现的场合
- **最小用法**：
  ```java
  @Service
  public class OrderService {
      private final PayClient pay;
      public OrderService(PayClient pay) { this.pay = pay; }  // 构造器注入
  }
  ```
- **代码位置**：`spring-context/.../DefaultListableBeanFactory.java:820`
- **高频度依据**：官方示例中出现 47 次；`@Autowired` 在工程中命中 128 处（scan 报告）
```

五个字段缺一不可。**「高频度依据」必须有，不能拍脑袋打星。**

## 高频度判定依据

按可信度从高到低：

1. **扫描统计** —— 本工程中该能力相关 API/注解的命中次数（`scan_project.py` 输出）
2. **官方示例占比** —— 官方 repo 的 `samples/` 或文档示例中出现次数
3. **文档篇幅** —— 官方文档中该章节的字数占比
4. **默认开启** —— 配置项默认是开启的（说明官方认为你会用）
5. **Stack Overflow / Issue 热度** —— 检索所得，需标注来源与检索时间

标记：★★★（核心，天天用）/ ★★（常用）/ ★（进阶或低频）

**每一条都要能在「高频度依据」里说出是上面哪一条支撑的。**

| 编号 | 能力 | 一句话 | 高频度 | 代码位置 |
|------|------|--------|--------|----------|

<每条展开五字段>

## 常用能力（N 条）
（表格形式，只展开 ★★★ 的）

（表格 + 简短说明，标注风险）

核心能力必须全部展开；常用能力只展开高星的。

## 优质判据

- [ ] 三级分层清晰，核心能力 ≤8 条
- [ ] 每条五字段齐全
- [ ] 高频度有明确依据（不是拍脑袋）
- [ ] 最小用法片段是从真实代码来的，不是凭记忆写的
- [ ] 代码位置精确到行号
- [ ] 进阶能力标注了风险

## 常见错误

- ❌ 把配置项当成能力（"支持 200 个配置项"不是能力）
- ❌ 把实现细节当成能力（"使用三级缓存"是机制不是能力）
- ❌ 能力之间没有去重（"依赖注入"和"自动装配"写成两条）
- ❌ 高频度全打 ★★★（失去区分度）
- ❌ 代码位置写目录不写行号
