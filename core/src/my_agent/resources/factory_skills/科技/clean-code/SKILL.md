# 功能：Clean Code 与架构原则

详细材料见 `assets/solid.md`、`assets/clean-architecture.md`。

## 适用场景
评审或重构代码质量、设计模块/类/函数、被要求「清理代码」或改善结构、评估架构边界、命名、降低耦合提高内聚。触发词：clean code、SOLID、clean architecture、code smells、单一职责、依赖倒置。

## 步骤（评审/写作时按此顺序检查）
1. **可读性**：别人 30 秒能看懂吗？
2. **命名**：名字是否揭示意图？（类=名词，函数=动词，布尔=疑问式如 `isActive`；名字需要注释就是名字错了）
3. **函数大小**：能提取吗？（小，再小；一件事；理想 0–2 个参数，3+ 是坏味道；无副作用；命令查询分离；DRY——三处重复才是阈值）
4. **单一职责**：每个单元是否只有一个变更原因？
5. **依赖**：是否指向稳定/抽象？
6. **耦合**：是否有不必要的耦合？（迪米特法则：不 `a.getB().getC().doThing()`）
7. **错误处理**：是否干净一致？（偏好异常/Result 而非错误码；不返回/传 null；try-catch 放函数顶层；异常类按调用者需求定义）
8. **测试**：是否具备、干净、测行为？

## 核心原则

- **童子军规则**：每次提交都让代码比之前更干净。
- **对象 vs 数据结构**：对象隐藏数据暴露行为；数据结构暴露数据无行为；不要混用。
- **SOLID**（详见 `assets/solid.md`）：单一职责（一个变更原因，一个 actor）、开闭（对扩展开、对修改闭，用多态而非条件）、里氏替换（子类型可替换基类型且不破坏行为）、接口隔离（多专用接口优于一个通用接口）、依赖倒置（依赖抽象不依赖具体）。
- **Clean Architecture**（详见 `assets/clean-architecture.md`）——**依赖规则**：源码依赖必须指向内层（高层策略）。
  ```
  Frameworks & Drivers → Interface Adapters → Use Cases → Entities
  （外）                                          （内）
  ```
  内层不知道外层；跨边界数据是简单 DTO/值对象，绝不用框架特定类型；数据库、Web、框架都是细节。
- **组件原则**：共同闭包（一起变的一起放）、共同复用（别强迫依赖不用的东西）、稳定依赖（依赖指向稳定方向）、稳定抽象（稳定的组件应抽象）。
- **坏味道**：僵化（小改引发连锁）、脆弱（改一处坏无关处）、固着（难复用）、不必要的复杂（过早抽象）、不必要的重复（复制粘贴）、晦涩（难理解）、长函数/大类/长参数列表/布尔标志/按类型 switch。
- **TDD**：三定律——先写失败测试、只写够失败的测试、只写够通过的代码；F.I.R.S.T.（快、独立、可重复、自校验、及时）；测边界与行为，不测实现。

## 输入输出
- 输入：待评审/待写的代码。
- 输出：按上述顺序的检查结论 + 具体改进建议/重构（行为不变）。

## 注意事项
- 原则是默认倾向，不是盲从规则——用判断，但默认倾向干净。
- 注释：好代码自解释；只保留法律/信息/澄清意图/后果警告/TODO 类注释；删除被注释掉的代码（版本控制记得住）；不要写复述代码的注释。
- 格式化：报纸隐喻（高层摘要在上细节点下）；相关函数就近；调用者在被调用者之上；行短。

## 可复用示例
- 命名：`r` 不是 URL，用 `url`；`isValid`、`hasPermission`、`canExecute`。
- 错误处理：`checkPassword` 不应顺带初始化 session（无副作用）；命令查询分离——要么做事，要么答问题，不要两者兼有。
- 组件：`OrderRepository` 依赖 `OrderStore` 抽象而非具体 DB 类（依赖倒置 + 数据库是细节）。
