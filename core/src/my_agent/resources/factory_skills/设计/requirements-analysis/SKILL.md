# 需求分析（对话式需求提取与分解）
## 适用场景

- 通过多轮对话把一句简短想法转化为详细需求文档
- 把 EPIC 分解为需求与用户故事
- 对多个需求做优先级排序（MoSCoW / RICE / 价值 vs 成本 / Kano / 加权评分）
- 识别利益相关者与依赖关系、定义验收标准、创建需求文档
- 触发词：需求分析、需求记录、EPIC 分解、用户故事、优先级排序、验收标准、需求文档

## 步骤

### 单个需求分析（六步）

1. **初始需求捕获**：一句话描述需求是什么？解决什么问题？谁提出的？
2. **利益相关者识别**：最终用户？业务负责人/赞助人？技术利益相关者？是否有合规/安全相关方？
3. **详细需求规格**：
   - 功能性需求：需要哪些具体功能？用户工作流程？需要捕获/显示哪些数据？
   - 非功能性需求：性能（响应时间、吞吐量）、安全（认证/授权/加密）、可扩展性（并发、数据量）、可用性（正常运行时间、灾难恢复）
   - 业务背景：业务价值、成功指标、预期 ROI
4. **时间线与依赖**：硬性截止还是灵活？依赖其他项目/系统？外部因素（监管、市场）？一次性交付还是分阶段？
5. **验收标准（Given-When-Then）**：
   ```
   Given [前置条件]
   When [操作]
   Then [预期结果]
   ```
6. **文档编写**：按需求文档模板产出。模板与示例见 `assets/requirements/`：`requirement-template.md`（需求文档完整模板）、`epic-template.md`（EPIC 模板）、`user-story-template.md`（用户故事模板）、`prioritization-methods.md`（优先级方法详解）、`complete-example.md`（完整示例）。

### EPIC → 需求 → 用户故事分解

```
EPIC（业务计划）
├── 需求 1（功能/能力）
│   ├── 用户故事 1.1
│   └── 用户故事 1.2
└── 需求 2
    └── 用户故事 2.1
```

1. 从 EPIC 开始：识别高层次业务计划，定义愿景与目标。
2. 分解为需求：拆成逻辑功能或能力。
3. 需求拆为用户故事：从用户角度、按 INVEST 标准编写。
4. 验证层级：所有用户故事汇总到需求，所有需求汇总到 EPIC。

## 优先级方法选择

| 方法 | 最适合 | 何时使用 |
|------|--------|----------|
| MoSCoW | 简单优先级，明确必需项 | 快速分类，明确必须有 |
| RICE | 数据驱动决策 | 有量化数据，需客观评分 |
| 价值 vs 成本 | 可视化优先级 | 快速决策，二维评估 |
| Kano 模型 | 关注用户满意度 | 以用户为中心，识别惊喜点 |
| 加权评分 | 自定义标准 | 多维度评估，利益相关者对齐 |

## 输入输出

- **输入**：一句话想法 / EPIC / 现有需求描述。
- **输出**：需求摘要、利益相关者清单、功能与非功能需求、时间线与依赖、可测试验收标准、结构化需求文档。

## 注意事项

- **主动倾听**：开放式提问，复述确认，不假设。
- **迭代细化**：先高层次再补细节。
- **可追溯**：用户故事链接到需求，需求链接到 EPIC。
- 常见陷阱：细节不足（用 5W1H）、范围蔓延（明确边界 + 变更控制）、遗漏利益相关者、不切实际时间线、忽视非功能性需求、优先级排序不当（强制排序）、缺乏验收标准。
- 验收标准必须可测试，禁止"提升体验"这类不可验证表述。

## 可复用示例

```
需求：支持批量导入客户
Given 用户已进入客户列表页且拥有导入权限
When 用户上传含 100 条客户的 CSV 并点击"导入"
Then 系统在 30 秒内返回成功 98 条、失败 2 条的结果，并给出失败行原因
```
