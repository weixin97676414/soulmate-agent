# 知乎高赞回答写作

输入一个知乎问题（可附用户的素材、经历、观点），输出一篇符合知乎社区气质、具备高赞基因的回答。支持硬核长文与抖机灵短答双模式，无需 API Key、即装即用。

## 适用场景

- 经验求助型（怎么办 / 如何做）
- 观点讨论型（如何看待 / 为什么）
- 体验分享型（是一种什么体验）
- 知识科普型（XX 是什么原理）
- 把已有文章改写成知乎体
- 短篇故事的知乎回答式包装

不适用：学术论文代写；含真实在世人物的虚构；一句话短答或纯情绪宣泄（本技能主打 1000-4000 字回答，抖机灵模式例外）。

## 开始前需要的信息

- 问题原文（必填）
- 用户的真实身份要素：职业与年限、量化成果、亲历事件、失败经历（用于人设，**没有就说不有，绝不虚构**）
- 可用的素材、数据、案例、观点
- 目标平台语气、是否商业/好物内容、有无禁用表达

信息不足时先列缺口和影响，再基于明确假设给首版。

## 执行流程

### 第一步：拆解问题（决定整篇打法）

拿到问题先做三个判断：

1. **问题类型**：经验求助型 / 观点讨论型 / 体验分享型 / 知识科普型。
2. **情绪浓度**：高情绪问题（婚恋、职场不公、贫富差距）靠共鸣与故事；低情绪问题（技术、学术）靠信息密度与严谨。
3. **竞争格局**：让用户描述现有高赞（或贴出现有高赞），找「没被写过的角度」——同角度写得再好也难超越先发高赞。

据此选模式：
- **硬核长文模式**（默认）：1500-4000 字，适合经验、科普、观点型问题。
- **抖机灵模式**：50-300 字，适合娱乐向、段子向、「神回复」生态的问题，用户明确要求或问题明显是段子场时才用。

### 第二步：确定人设

高赞回答的隐形前提是「这个人有资格回答这个问题」。按 `references/answer-structures.md` 的「人设注入四步法」执行：

- 盘点真实身份要素（职业、年限、亲历事件、量化成果、失败经历）。
- **红线：用户没有的经历绝不虚构**。无相关身份时改用「观察者人设」（我研究过/我访谈过/我整理了公开资料）、「同路人人设」（我也踩过这个坑）或「拆解者人设」（我把公开资料拆了一遍，按可信度排序）。
- 人设要素在回答中出现 2-3 次：开头亮一次，中段用细节坐实一次，结尾轻带一次。
- 主动暴露一处小局限（「我的经验局限于 X」），可信度反而更高。

### 第三步：写开头（决定 80% 的命运）

知乎信息流只露出前 50-80 字，开头从 `references/openings-library.md` 四大类中选型：

- **反常识体**：先推翻问题预设或大众答案（适合观点型）
- **亮身份体**：一句话立住「我有资格答」（适合经验型）
- **直接给结论体**：第一句就是答案，后文论证（适合求助型、科普型）
- **故事切入体**：一个具体到有画面的场景开场（适合体验型、情感型）

注意：「谢邀」开头已是老梗，仅用户明确要求怀旧风时使用，且要用自嘲变体。

### 第四步：按结构填充正文

主体沿用 `references/answer-structures.md` 的「故事-干货-反转」三段式或三种变体（清单式 / 递进式 / 驳论式）。核心纪律：

- 每 300-500 字一个分割线或小标题，制造「往下滑的理由」。
- 干货部分必须有**具体名词、具体数字、具体步骤**——「多读书」是废话，「先读完《XX》第 3 章 + 《XX》的方法论部分」才是干货。
- 至少埋 1-3 个「金句点」（可被单独截图转发的句子），位置放段落末尾、独立成段。
- 结尾设互动钩子：开放式问题、立场站队，或「评论区补充」邀请。

按问题场景套用差异化结构：

| 场景 | 开头公式 | 正文结构 | 金句风格 | 结尾 |
|------|----------|----------|----------|------|
| 职场成长 | 「作为一个过来人…」 | 经历→方法→结果→建议 | 扎心+实用 | 鼓励行动 |
| 情感话题 | 「看到这个问题很有感触…」 | 共情→观点→案例→价值观 | 温柔+通透 | 温暖收尾 |
| 干货科普 | 「直接说结论：…」 | 定义→原理→应用→资源 | 硬核+清晰 | 延伸阅读 |
| 热点话题 | 「这件事的关键不在…而在…」 | 事件→角度→分析→立场 | 犀利+深度 | 开放讨论 |

- 正文分点论证（3-5 点），每点 150-300 字，带加粗小标题。
- 案例用真实案例或可核实数据支撑。

### 第五步：排版与合规终检

按 `references/zhihu-rules.md` 执行：

- 排版：单段 ≤5 行；每屏最多 1-2 处加粗，加粗结论句而非形容词；全文风格统一；**禁 emoji**；参考来源放文末。
- 引流合规：检查是否有站外导流表述、二维码暗示、「私信我」钩子——全部去除或改合规写法。
- 社区红线：医疗建议加免责；法律财税投资注明「不构成专业建议」；不编造数据来源；不代写学术作业、不编造论文引用。

## 输入输出

- **输入**：问题原文 + 用户真实素材/观点。
- **输出**：一篇可直接粘贴的回答正文，外加策略说明与发布建议。

## 输出模板

```markdown
# 知乎回答：{问题原文}

## 策略说明（3 行内）
- 问题类型/模式：{硬核长文 or 抖机灵}
- 切入角度：{与现有高赞的差异点}
- 人设：{使用的真实身份要素}

## 回答正文
{完整可直接粘贴的回答，含分割线与加粗标记}

## 发布建议
- 首段前 50 字露出效果预览：「{截取}」
- 建议发布时间：{工作日 12-14 点 / 21-23 点；周末上午}
- 互动预案：{预判评论区的 2 个高频质疑及回复口径}
```

## 方法论要点

1. **知乎的核心货币是「认知增量」**：读者点赞理由是「学到了 / 被说服了 / 被代表了」三者之一，一篇只主打一种。
2. **具体性是知乎体的命根**：时间具体到月份、金额具体到百位、书名具体到章节、对话具体到原话。
3. **先抑后扬的可信度设计**：主动暴露一个小失败或局限，比全程正确更可信。
4. **赞同的本质是社交表态**：写情绪段落时问「读者点赞转发时在宣告什么立场？」答案越清晰，赞越多。
5. **反对票机制**：观点激烈但论据薄弱会被反对压下去，每个激烈观点后必须紧跟论据（数据/亲历/引文三选一）。
6. **长文的「滑动节奏」**：每一屏都要有视觉锚点（加粗句/分割线/短段落/清单），连续三屏纯大段文字必掉读完率。
7. **抖机灵的时机纪律**：只在问题本身娱乐化、且已有抖机灵高赞的生态里使用；严肃求助帖下抖机灵会被反对+举报。
8. **发布不是结束**：前 2 小时的赞同速度影响进推荐池，用「互动预案」为发布后运营做准备。

## 示例

**用户输入**：25 岁开始学编程晚吗？

**开头**：不晚。我就是 25 岁开始学的，现在是大厂高级开发。

**正文**（节选）：
一、25 岁反而是最好的年纪——22 岁毕业，3 年职场已经让你知道什么是自己不想要的。
二、我用两年证明的事——第一年学完基础+两个项目；第二年跳槽成功，薪资翻倍。
三、但要说实话：你不会再有 20 岁的精力——路径要对、方法要对、效率要对。
**金句**：> 25 岁学编程不晚，但要用 30 岁的打法——拼方法，不拼蛮力。
**结尾**：想听具体自学路径和避坑清单，评论区告诉我，我再写一篇。
**评论区互动建议**：你是什么时候开始转行的？/ 你学编程踩过最大的坑是什么？

## 红线与免责

1. **绝不虚构用户不具备的身份与经历**。用户坚持编造时明确拒绝，提供「观察者/同路人」替代方案。
2. **绝不写站外引流内容**：不出现微信号、二维码、外链导流、「私信领资料」等表述。
3. **专业领域加免责**：医疗健康注明「不能替代医生诊断」；法律、财税、投资注明「不构成专业建议」。
4. **不代写学术作业、不编造论文引用**：引用数据与文献必须用户提供或注明「请自行核实」。
5. 赞同数受问题热度、发布时机、账号权重等多因素影响，本技能不构成任何流量承诺。
6. 涉及真实发送/发布/付费/删除/权限或生产变更时，必须由用户明确授权。
